## Key findings

### `Widget` / `WidgetGroup` — menu/network coupled

- `Widget` carries a `ModularUI gui` field and a `WidgetUIAccess uiAccess` field,
  set via `setUiAccess(WidgetUIAccess)` / assigned when added to a `ModularUI`.
- `Widget` exposes networking/lifecycle methods clearly designed to be driven by a
  `ModularUI`/`ModularScreen` container tick loop: `writeInitialData`,
  `readInitialData`, `detectAndSendChanges`, `updateScreen`, `writeUpdateInfo`,
  `writeClientAction`, `handleClientAction`, `readUpdateInfo`.
- `WidgetGroup` *can* be constructed standalone (`WidgetGroup()`,
  `WidgetGroup(int,int,int,int)`, `WidgetGroup(Position)`,
  `WidgetGroup(Position, Size)`) without a `ModularUI` — but it still has
  `setGui(ModularUI)` and inherits all the network/lifecycle plumbing from
  `Widget`. Nothing in the verified API guarantees these methods are safe
  no-ops when `gui`/`uiAccess` are null; this was not proven safe by static
  inspection alone (no client/visual test available in this environment).
- Using the full `Widget`/`WidgetGroup` tree as the backbone of a persistent
  Forge `IGuiOverlay` would risk invoking menu/container-oriented code paths
  that were never designed to run outside a `ModularUI`/screen lifecycle —
  exactly the risk flagged by the repo `plan.md` Phase 2 decision rule.

### `IGuiTexture` and its implementations — pure rendering, no menu coupling

- `IGuiTexture` is a plain interface: its only abstract method is
  `draw(GuiGraphics, int x, int y, float width, float height, int, int)`.
  No `ModularUI`, no `WidgetUIAccess`, no networking methods.
- `TransformTexture` (abstract base for `ResourceTexture`, `ProgressTexture`,
  `GuiTextureGroup`) holds only `xOffset/yOffset/scale/rotation` and exposes
  `draw(...)`/`drawSubArea(...)` — again, no menu/container dependency.
- `ResourceTexture(ResourceLocation, float u, float v, float w, float h)` /
  `ResourceTexture(ResourceLocation)` — draws a sprite region directly via
  `GuiGraphics`; has `setColor(int)`, `setDynamicColor(IntSupplier)`,
  `setImageWidthHeight`, `getSubTexture(...)`. Fully self-contained.
- `ProgressTexture(IGuiTexture empty, IGuiTexture filled)` — drives a
  fill-bar look via `setProgress(double)` / `getProgress()` /
  `setFillDirection(FillDirection)`. No container coupling.
- `GuiTextureGroup(IGuiTexture...)` — composites multiple `IGuiTexture`s into
  one draw call. No container coupling.

## Decision (per repo `plan.md` §Phase 2 decision rule)

**LDLib's full `Widget`/`WidgetGroup` framework is NOT a safe fit for a
persistent Forge `IGuiOverlay`** without constructing an inappropriate
menu/screen lifecycle (`ModularUI`/`WidgetUIAccess`), and this environment has
no way to actually launch the client to prove otherwise.

**LDLib's texture primitives (`IGuiTexture`, `ResourceTexture`,
`ProgressTexture`, `TransformTexture`, `GuiTextureGroup`) ARE safe** to call
directly from XenoPixels-owned overlay code: they are plain rendering objects
with a `draw(GuiGraphics, ...)` entry point and no menu/network coupling.

**Recommendation for later phases (4+, out of scope this session):** build the
HUD's visual pieces (bars, portrait frame, icons) using `ResourceTexture` /
`ProgressTexture` / `GuiTextureGroup` invoked from the existing Forge
`IGuiOverlay` registrations — do NOT attempt to host a `WidgetGroup`/`ModularUI`
tree inside the HUD render pass.

## Addendum (Phase 4, in-game test): `IGuiTexture#draw` real parameter order

`javap`'s type-only signature listing for
`draw(GuiGraphics, int, int, float, float, int, int)` does **not** tell you
the parameter *names*/order. A live in-game test of Phase 4's first
`XenoHudView` cut showed nothing rendering (confirmed by screenshot — the
renderer-switch toast fired but no HUD pixels appeared).

Disassembling `TransformTexture.draw`/`ResourceTexture.drawInternal` with
`javap -c` (bytecode, not javadoc) showed the true call chain:

```
draw(graphics, A, B, C, D, E, F)
  -> preDraw(graphics, C, D, E, F)          // floats forwarded as (x, y, width, height)
  -> drawInternal(graphics, A, B, C, D, E, F)
  -> postDraw(graphics, C, D, E, F)
```

i.e. the two leading `int`s are **mouseX, mouseY** (not x, y), the two
`float`s are the actual **x, y** position, and the two trailing `int`s are
**width, height** (not mouseX, mouseY). Verified signature:

```java
void draw(GuiGraphics graphics, int mouseX, int mouseY, float x, float y, int width, int height)
```

`XenoHudView` originally called `texture.draw(graphics, x, y, width, height, 0, 0)`,
which the real signature interpreted as `mouseX=x, mouseY=y, x=width, y=height,
width=0, height=0` — a correctly-positioned-nowhere, zero-size quad, hence
invisible. Fixed by reordering every call site to
`texture.draw(graphics, mouseX, mouseY, x, y, width, height)`.

**Lesson for future phases:** `javap` type signatures are necessary but not
sufficient to safely call an unfamiliar LDLib method — always confirm actual
parameter order with `javap -c` bytecode tracing (or a live render test)
before trusting a "looks like a normal GUI-lib signature" assumption.

**Update — user-confirmed live test (in-game screenshot):** after reordering
the `draw()` call sites, `/xenohud renderer ldlib` now renders correctly:
portrait frame square, full-width red HP bar, full-width yellow KI bar, and
all 16 blue stamina segments lit, all positioned and proportioned as expected
at the configured `x=10,y=10,scale=0.5`. This is the first Phase 4 acceptance
criterion ("both legacy and LDLib renderers can be compared with the same
snapshot") **manually confirmed**, not just compiled.
