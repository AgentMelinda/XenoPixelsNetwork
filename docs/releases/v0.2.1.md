# v0.2.1

- **Released:** 2026-09-07
- **Build:** `0.2.1-1.21.1`
- **Platform:** Minecraft 1.21.1 / NeoForge 21.1.238 / Java 21, against DragonMineZ 2.1.3
- **Git range:** `v0.1.11..v0.2.1`
- **Supersedes:** [the 0.1.14 development draft](UNRELEASED-0.1.14-1.21.1.md)

**There was no 0.2.0 release.** The work below was developed under a `0.2.0` working version but was
never tagged or published, so it ships here as the first `0.2.x` release.

**Verification status, stated up front:** everything here compiles and is covered by unit tests
where the logic is pure (303 tests across 53 classes, 0 failures), and external signatures were
checked against the DragonMineZ jar and the NeoForge sources. **Most of it has not been observed in
a running client.** See *Known limitations* at the end, which is not boilerplate — it names what is
still broken.

## Scope

This version is an evidence-based correctness pass over the features listed in `CHANGELOG.md`,
not new gameplay. Every item below was traced to a specific source path before being changed;
external signatures were verified against `libs/dragonminez-2.1.3.jar` and the NeoForge sources
jar rather than assumed from naming.

## Input ownership

- Native weapons and active ki weapons no longer also produce Xeno fists. Ownership is decided by
  one shared predicate (`combat/FistInputPolicy.java`) that both the client input path and the
  server packet handler consult, so the two can no longer disagree and apply damage twice.
- Empty-hand attacks fall back to Minecraft's and DragonMineZ's native attack when Xeno does not
  own the input — including when the combo and charge features are switched off, where Attack was
  previously left unbound with nothing replacing it.
- Left-click mining works again. The ownership gate runs at `Minecraft.startAttack` /
  `continueAttack` (mixin priority 1100, ahead of DragonMineZ's own head hook) instead of issuing
  a contradictory second `continueAttack(true)` after native processing had already aborted the
  dig. How the dig itself is preserved is described under *Left click, mining and guard* below.

## Left click, mining and guard

- A punch breaks blocks, and mining is fully native again. DragonMineZ's punch and kick sequence is
  stood down at `PlayerAttackHelper.canAttack`, which DMZ consults in exactly the two places its
  melee starts, rather than by cancelling the click. Nothing vanilla is cancelled on a block target,
  so digging behaves exactly like plain left click — with a tool in hand as much as with fists.
  Minecraft's own `gameMode.attack` is still suppressed away from a block so it cannot double up
  with an Xeno fist, which is the one thing that could land two hits from one press: DMZ yields a
  block to mining only when nothing stands in front of it, so a mob against a wall used to produce
  a DMZ punch and an Xeno fist together.
- Fists and the charged fist no longer switch off whenever a block is under the crosshair. The
  ownership rule is split: what the crosshair points at decides whether the *native* attack is
  suppressed, never whether Xeno fists run. Previously a charge in progress was cancelled the
  moment the view swept across terrain, and the tap-then-hold arm window was wiped with it.
- Punches read Xeno's own punch binding instead of Minecraft's Attack key. `CHARGE_FIST` defaults
  to left click, so a stock profile behaves identically, but unbinding Minecraft Attack — a
  reasonable thing to do when Xeno owns the click anyway — used to silently kill every punch,
  combo and charged fist while the Xeno binding still sat on left click. With Attack unbound the
  block dig is driven from the Xeno binding too, and stands down whenever the vanilla key is the
  one being held, so a dig is never issued twice. Mining with a tool needs Minecraft Attack bound,
  since an item in hand takes Xeno out of the click entirely — with Attack bound, which is the
  default, tool mining is untouched.
- The startup repair that forced Minecraft Attack back onto left click no longer overrides a
  deliberate unbind. It now only fires when the Xeno punch binding is *also* cleared, which is the
  one profile with no way to attack or mine at all.
- Guard no longer stops you attacking with something in your hand. Xeno Guard sits on right mouse,
  so right-clicking with any item raised it, and a raised guard suppressed both DragonMineZ's melee
  and Minecraft's own attack. Guard still engages with an item held, so blocks can be placed while
  guarding, but it only suppresses the attack when both hands are empty and no ki weapon is out —
  the same condition DMZ applies to its own block, which never raises with an item held. With an
  item there is no Xeno fist to throw, so there was nothing to protect.
- Guarding no longer blocks mining. Both `Minecraft.startAttack` and `Minecraft.continueAttack`
  bail out on a cancelled click hook, so raising guard used to kill the initial dig and every tick
  of dig progress.

## Rush

- The four Xeno rush strikes unlock for every player. They are Xeno entries injected into DMZ's
  predefined strike registry, so no DMZ progression can grant them; gating the only unlock path on
  an operator permission left them permanently locked for ordinary players, including in
  single-player without cheats. The permission node stays declared but is no longer consulted.
- Double-tapping W at a locked target that is still on the ground now says so instead of doing
  nothing. A rush still follows a launcher, as in BT3.

## Rush camera

- The rush camera stops thrashing at contact range, which is where all four Xeno rush strikes
  actually land. Aiming at a target is an angular problem and the rate needed to track one grows
  without bound as distance shrinks: at six blocks a half-block sidestep is about five degrees, at
  half a block it is nearer forty-five, and the pitch term had the horizontal distance as its
  denominator so it ran to ±90° and swung tens of degrees from centimetres of jostling. The earlier
  deadzone, easing and per-tick cap bounded how fast a correction could be applied but not the error
  demanding it, so the assist sat on its cap and never settled.
- The assist now fades to **nothing** inside contact range — where the fighter is already facing the
  target and the maths is least trustworthy — ramps in smoothly with distance, floors the pitch
  denominator, and aims at mid-body rather than eye-to-eye. The arithmetic moved into a pure
  `RushCamera` class with tests that pin the divergence itself, not just the happy path.

## Camera

- The rush and chase view assist is gentle and has a single writer. It eases far more slowly, only
  corrects outside a small deadzone so ordinary mouse aim is left alone, caps how far one tick may
  move the view, and eases pitch slower than yaw because a launched target climbs fast. It no
  longer overwrites the previous-tick body rotation, which had removed the renderer's
  interpolation and snapped the body every tick, and it is no longer applied twice in the same
  tick during a rush.

## Shi Shin No Ken and Zanzoken

Both are the same idea used twice — a copy of you standing somewhere you are not — so both run on
one `XenoCloneEntity`. A copy is a plain entity, not a living one: it never paths or decides
anything, it draws as its owner through the normal render dispatcher (so it inherits your live
DragonMineZ hair, form and aura for free), and it pops on the first hit rather than tracking health.

- **Shi Shin No Ken** divides you into four bodies (`multiFormBodies`) that hold formation and turn
  as you turn. The bodies **burst out of yours** and travel to their places rather than appearing
  beside you, and the fighter is swapped into the **back slot** in the same motion — an opponent in
  front meets the copies first and cannot tell from position which body can actually be hurt. Each
  copy is a living body carrying a share of your health.
- **Copies wear the fighter's real DragonMineZ body** — hair, body type, race parts, colours, form
  and aura — instead of a plain player model. Each copy is drawn through DragonMineZ's own player
  renderer against a proxy identity of its own, so it gets its own aura entry and its own GeckoLib
  animation state rather than collapsing into the fighter's. This turned out to be far smaller than
  feared: the NPC path is elaborate only because an NPC has no DragonMineZ character to begin with,
  while a copy's owner is a player who already has one, so the proxy takes the owner's whole
  `StatsData` in a single `copyFrom` and inherits everything at once. Refreshed on an interval
  rather than per frame, and switchable off (`cloneDmzAppearance`) back to the plain model.
- Copies carry the fighter's name, and the clone entity finally has a translation. Without either,
  the renderer fell back to the entity type's display name and drew the raw `xenopixelsmod.clone`
  key across the screen.
- Reuniting draws the bodies home. Each copy retraces the arc it came out on and vanishes as it
  reaches the fighter, instead of being deleted where it stood. Full power returns the instant the
  technique is dropped rather than waiting for the animation.
- Copies no longer corrupt the frame. The previous renderer moved the fighter's live entity to each
  copy's position for one draw and restored it; DragonMineZ's aura pass is deferred, read that
  entity again afterwards, and painted aura geometry between the two positions — pink streaking
  across the sky, flickering copies, and the fighter's own aura breaking on every split. Copies are
  now drawn as themselves, wearing the fighter's skin on a vanilla player model, touching nothing
  else in the frame. The DragonMineZ appearance is the honest cost until each copy carries its own
  proxy identity.
- Copies hold still. Easing their position on the server as well as on the client meant two
  smoothings fighting each tick; the settled slot position is now sent exactly and the client does
  the interpolation.
- Copies face whoever the fighter has locked on, read from DragonMineZ's own homing slot, instead
  of copying the fighter's head and staring at nothing whenever he glanced away.
- **Copies fight.** A combat bridge (`CloneCombatBridge`, `CloneCombatPolicy`, `CloneSplitState`,
  `CloneTargetTracker`) drives copies through the existing NPC dispatchers so they throw ki and
  strikes at the fighter's target. Added late in development by another hand and **not observed
  working in a game by the author of these notes** — treat it as new and unproven. One crash from
  it was found and fixed during development: `NpcGeckoAnim.playAttack` reflectively read
  `EntityNPCInterface.display` off a copy and threw, crashing the server on entity tick. Every
  reflective NPC access reachable from a copy was subsequently audited and either type-guards or
  catches `Throwable`.
- **Mastery** (0–1000, persisted per fighter) closes the power split the technique normally costs.
  At zero each body hits for a quarter; at full mastery dividing is free and every body hits at
  full strength. Toggle to divide and reunite; dividing costs ki, reuniting is free so an empty bar
  can never strand you. **Each body hits for a quarter.** That division is applied once, on the
  damage event, so it covers this mod's ten melee paths *and* DragonMineZ's own attacks and cannot
  drift out of step with the body count. Dividing buys angles and a target the opponent has to
  guess at, never raw damage. Logging out or dying reunites you.
- **Zanzoken** throws a **closed ring of copies around the attacker** rather than leaving one
  fading image where you stood. Each copy faces inward at whoever is trapped in it, and holds
  position — a ring that drifts stops being a ring. The dust silhouette remains selectable via
  `zanzokenGhostAfterimage`.
- Settings: `zanzokenRingClones`, `zanzokenRingRadius`, `multiFormEnabled`, `multiFormBodies`,
  `multiFormKiCost`.
- Shi Shin No Ken ships **unbound**, like Zanzoken.

## Zanzoken

New technique: the afterimage dodge. **Ships unbound** — every key near the movement hand is
already taken by vanilla, DragonMineZ or this mod, so pick one in Controls.

- **How it works:** tap the key *as a hit is about to land*, not before a fight. The press opens a
  0.4s read (`zanzokenWindowTicks`, 8 ticks) and costs ki whether or not anything arrives; only a
  melee hit landing inside that window is dodged. The action bar shows "Zanzoken: reading…" on a
  press that opened, "not ready" while on cooldown, and "ZANZOKEN!" when a dodge actually lands, so
  a press with nothing incoming is distinguishable from a technique that is not firing.
- Tapping the key opens a short read rather than a stance. A melee hit that lands inside the window is
  cancelled outright, you are granted invulnerability ticks, an image of you stays where your body
  was, and you reappear behind the attacker. Mistime it and the ki is spent for nothing, which is
  what separates it from a block.
- The afterimage is **you** — the fighter is re-rendered at the position they vanished from through
  the normal entity render dispatcher, so with DragonMineZ installed it arrives wearing their real
  hair, active form, aura and race parts with no appearance code of ours. Purely visual and purely
  client-side; no entity is spawned.
- The existing dust silhouette is kept and still selectable, for anyone who prefers it or whose
  client cannot draw the copy: `zanzokenGhostAfterimage`.
- Uses DragonMineZ's own `zanzoken` sound, which ships in its jar and nothing had been playing.
- Settings: `zanzokenEnabled`, `zanzokenKiCost`, `zanzokenWindowTicks`, `zanzokenIFramesTicks`,
  `zanzokenCooldownTicks`, `zanzokenGhostAfterimage`.

## Combat state no longer survives a world reload

- Every timing map in `Bt3CombatEvents` is keyed on `MinecraftServer.getTickCount()`, which
  restarts at zero on each world load, while the maps are static and outlive the server inside a
  single-player client. A cooldown stamped late in one session therefore sat far ahead of the next
  session's clock. Zanzoken reported "not ready" for as long as the previous session had run — half
  an hour of play meant half an hour of a dead technique. Super-counter windows and guard stuns are
  stamped from the same clock and carried the same latent fault.
- The state is now cleared on server stop and on logout, and the window logic additionally treats a
  deadline impossibly far ahead of the current clock as stale rather than trusting it, so a missed
  cleanup path costs one wasted press instead of silently disabling the move.
- Zanzoken's three refusals — disabled, cooling down, not enough ki — now say which one they are.
  The last used to fail silently.

## Mixin robustness

- The technique-unbind mixin reaches into DragonMineZ's own menu internals, so it moved out of the
  required mixin config and into the DMZ-gated compat one. A DragonMineZ update that renames those
  internals now costs the Unbind button rather than crashing the client — which is not theoretical:
  declaring the mixin against `Screen` while shadowing `getUiWidth`, which actually lives on the
  `ScaledScreen` ancestor, brought the game down the instant anything opened the skills menu.
  `@Shadow` resolves against the target class alone and does not walk the hierarchy.

## Combo dragon dash, and chases that stop killing you

- **Hold W through a combo beat and the hit launches the enemy and you go with it** — the fighter
  dashes after them on DragonMineZ Search Fly. It rides the launcher's existing homing window, and
  a homing chase skips both the near-range guard and the 50% success roll, so it reads as one
  continuous move rather than a hit followed by a coin flip. A W *tap* still only launches. This is
  read only while a combo string is live, so walking never triggers it, and it holds on the raw W
  key rather than the retired standalone hold-W gesture.
- **A chase no longer drops you to your death.** It ends wherever it ends, often far above the
  ground, and gravity came straight back with nothing between the fighter and the floor — players
  were dying to the landing rather than to the fight. Fall distance is now reset when a chase stops
  and fall damage is waived briefly afterwards, so the descent is survivable.

## Chase input

- Hold-Space and double-tap-hold-W no longer start a chase; both are off by default behind
  `bt3ChaseSpaceGesture` and `bt3ChaseWGesture`, and the code stays in place so either can be
  turned back on. Space is DragonMineZ's flight ascend, so every ascent with a lock-on was firing a
  chase attempt, spending ki and rolling the 50% success chance — the source of the repeated
  "Chase failed". W is the movement key and only worked behind gates that existed to stop walking
  forward from launching a chase.
- Chase now runs from its own binding, which ships unbound. If nothing can start a chase, the game
  says so once rather than leaving the technique looking broken.

## Chase, rush cost, guidance and unbinding

- A chase started from directly above its target dives onto it instead of climbing away. The
  landing point sits at the target's feet, so the path test clipped into the ground the target
  stands on and read a clear vertical drop as blocked; the detour then measured its height from the
  player's already-high position and climbed again every tick. The path test now aims at the
  target's body, ignores a hit within tolerance of the destination, only detours when the route
  actually goes somewhere horizontally, and measures clearance from the obstruction.
- Xeno rush strikes cost what the server config says, not thousands of ki. DragonMineZ derives a
  strike's cost from the caster's own power and ignores the declared base cost, which reached
  2924 ki per press at high level and made rush usable only on a full bar. Cooldown had the mirror
  problem: `getActualCooldown` re-reads DMZ's per-id config on every call, so a cooldown set at
  registration never survived. Both are now overridden for the four Xeno ids only — every other
  strike, including anything authored in DMZ's technique creator, keeps DMZ's numbers. New
  `rushKiCost` and `rushCooldownTicks` server settings.
- The chase camera has one authority. The server was still easing the player's yaw and pitch every
  tick alongside the client's own assist and the mouse; it now turns only the head and body other
  players see.
- Ki guidance follows the crosshair. The look-cone scan that auto-acquired whatever happened to be
  near the aim is gone, so a blast goes where it is pointed. A deliberate lock-on still homes, and
  healing ki still seeks a friendly under the crosshair since there is nothing else to steer it to.
- Techniques can actually be unbound from a slot. DragonMineZ's binding mode draws eight slot
  buttons and no way to empty one, and its `equipOrSwapTechnique` cannot express it either: an empty
  id is read as "already equipped", so it finds the first vacant slot and swaps, relocating the
  technique instead of removing it. An explicit Unbind button and the Delete shortcut now clear the
  slot directly through a Xeno packet.

## Chase and flight

- A chase request that the client rejects no longer reports itself as an active chase. Requested,
  pending and server-acknowledged states are distinct, and only the server's acknowledgement
  packet marks a chase active.
- A rejected request no longer deadens the held key: Space and a dedicated Chase binding keep
  retrying while held, so the chase starts the moment the move cooldown, range or ki reason
  clears. W keeps its deliberate tap-then-hold arming.
- Chase state is cleared on client logout and login, on world change, on death, on opening a
  screen, on entering a pilot seat, and when the feature is disabled. A connection lost without a
  clean server packet can no longer leave a chase latched on.
- The server accepts chase cancellation before the combat feature gate, so disabling combat mid-
  chase still releases it.
- Temporary flight is a lease, not a snapshot restore. The chase undoes only the Search Fly grant
  it made itself, and never resurrects flight that DragonMineZ disabled in the meantime — a ki
  depletion mid-chase now ends the chase instead of being overwritten by a stale snapshot. An
  already-active Search or Combat Fly is left alone entirely.

## Effect persistence

- Cured and expired effects no longer come back. The player transfer snapshot is refreshed at the
  real serialization boundary (`Entity.saveWithoutId`, before the entity is removed) and consumed
  once on restore, instead of lingering and replaying on the next reconnect. For players the
  snapshot exists only to survive the respawn clone; vanilla still owns ordinary effect saving.
- Negative effects survive a native CustomNPCs / My NPCs reset. Effects are captured before
  `EntityNPCInterface.reset` clears them and restored afterwards, rather than only on the fallback
  reset path where an empty capture could overwrite the saved list first.
- Resolving the optional NPC entity classes is now done once instead of per entity. The save hook
  runs for every living entity the game serializes, and the previous per-call `Class.forName`
  built a `ClassNotFoundException` on every miss when neither NPC mod was installed.

## Parties, cockpit and Hakai

- Sending an invitation no longer resets an existing party's friendly-fire choice. The configured
  default is applied only when the invitation actually creates the party.
- Cockpit input changes are detected across every field that is actually sent — stick pitch, roll
  and yaw and the mouse-aim, air-brake and auto-level flags, including the zero crossings that
  must stop keyboard torque — so a yaw input is no longer held until the keepalive fires.
- Restarting or retargeting a Hakai channel releases the glow the previous channel owned before
  the new one starts, and a channel only ever clears a glow it turned on itself.

## Executable regressions

New JUnit classes running on the existing NeoForge test runner
(`FistInputPolicyTest`, `ClientChaseFlightStateTest`, `ChaseFlightOwnershipTest`, `GlowLeaseTest`,
`NpcNegativeEffectPersistenceTest`, `PartyInviteDefaultsTest`, `FlightInputChangesTest`) cover
input ownership, chase request/acknowledge/reset transitions, flight-grant restore and stop
conditions, glow lease ownership and idempotent release, effect NBT capture/consume/clone against
real `MobEffectInstance` serialization, party creation defaults against real
`PartySavedData.PartyInstance`, and cockpit change detection including zero crossings.

`FistInputPolicyTest` additionally pins the split between "Xeno fists run" and "the native attack
is suppressed", so a block target can never switch punching off again.

Validated with `compileJava`, the targeted test classes above plus `XenoRushTechniquesTest` and
`Bt3ComboBeatTest`, and `jar`, `jarJar` and `serverJar` packaging. All runs passed with zero
failures.

## Bundled third-party data fix

This mod ships `data/northstar/worldgen/{placed_feature,configured_feature}/moon_{andesite,basalt,blackstone}_blob.json`.
A Northstar moon biome references those three placed features but nothing defines them, so the
`placed_feature` registry cannot freeze and the game dies at the world-selection screen with
`Unbound values in registry`. Removing this mod from a pack that contains Northstar therefore
*causes* that crash — confirmed from a user log this week. See
[`northstar-worldgen-fix.md`](../northstar-worldgen-fix.md) for why the ids are the pre-0.6 names
and why updating Northstar does not resolve it.

## Known limitations

- **Nothing here was reproduced in game.** These are static source and bytecode findings with unit
  coverage of the extracted decision logic. Runtime lifecycles — actual mixin application, real
  mining and attack sequences, live DragonMineZ flight interaction, real NPC resets and reconnects
  — remain unverified.
- **Known outstanding, reported after the fixes shipped:** pink aura streaking during Shi Shin No
  Ken persists and its cause is not established — the renderer change removed one real bug but was
  not the whole cause; DragonMineZ emissive geometry under Iris is a suspicion, not a conclusion.
  This was still present in the last user capture and its cause is not established.
- Copy combat and mastery accrual landed late in development and have had **no live combat
  acceptance**. An isolated dedicated server reached `Done` and answered a status ping; no player
  combat and no graphical client acceptance was performed.
- The per-copy DragonMineZ appearance path has not been observed in a running client;
  `cloneDmzAppearance` switches it off to the plain player model.
- Blue combat boxes are illustrative fixed geometry. They are not the server's authoritative range
  test and not an F3+B collision volume.
- The audit covered unreleased combat, input, chase, flight, effect persistence, Hakai, technique
  unbinding, and the released NPC lifecycle, HUD, party and cockpit paths. It is **not** a
  whole-repository clean bill of health. NPC scripting strategies and the full appearance surface,
  Sable physics, fleet/missiles/guidance, world generation, Create and ComputerCraft integration,
  permissions, the full forms and progression systems, packaging automation and shaders were not
  reviewed and are not implied correct.
